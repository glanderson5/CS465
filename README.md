Architecture
This project used two distinct frontend approaches. The customer-facing side was built with Express and Handlebars, a server-rendered approach where the server builds complete HTML pages and sends them to the browser on each request — the browser does little work beyond rendering what it's given. The admin side, by contrast, is an Angular single-page application: the browser loads one HTML shell, and Angular's router swaps components in and out without ever reloading the page. Data arrives as JSON and is rendered client-side. The SPA approach requires more plumbing — client-side routing, an HTTP interceptor, state management for login status — but enables richer, app-like interactivity that server-rendered pages can't easily match.
The backend used MongoDB largely because the trip data is naturally document-like — each trip is a self-contained record with no real need for joins across multiple tables, which made Mongoose a low-friction fit. That said, at this project's small scale, a relational database would likely have worked just as well; the real advantages of a NoSQL approach tend to show up more at scale or with messier, more variable data.
Functionality
JSON is a data format for exchange between systems, while JavaScript is a programming language for implementing logic. JSON's syntax is derived from JavaScript object notation, which is part of why it's the natural fit for a JS-heavy stack like MEAN. In this project, JSON is the connective tissue between frontend and backend: Angular's HttpClient serializes JS objects to JSON to send requests, Express parses that JSON back into JS objects to work with server-side, and the response — including the JWT itself — comes back as JSON and is deserialized into JS objects again on the Angular side.
One concrete refactor was consolidating the login and register methods in the Angular TripDataService into a single shared handleAuthAPICall helper, rather than duplicating the form-building and POST logic in two places. Reusable UI components, like the trip card component, offer similar benefits: at this project's scale the time saved is modest, but the underlying value — change the layout once and every trip updates, with each component independently testable — scales significantly as a project grows.
Testing
Layering authentication on top of the existing API made it noticeably harder to pin down where a bug was actually coming from. A single symptom — a connection error, a 404, something that looked like a CORS issue — could have multiple unrelated root causes (a crashed server, a wrong HTTP method, an uncaught database exception), and testing meant first isolating which layer was actually responsible before a fix was even possible. More console logging at each layer — confirming a request was received, an auth check passed or failed, a query returned what was expected — would have made many of these failures traceable instead of ambiguous. Testing authenticated endpoints specifically added the extra step of needing a valid token in hand before testing the thing actually being tested, which meant a login failure could masquerade as a failure somewhere downstream.
Reflection
The biggest takeaway from this course was seeing previously isolated pieces of the program finally work together. Earlier coursework treated SQL and databases as a powerful but standalone tool, without exploring how a database actually functions as part of a larger system. Similarly, JS and HTML had mostly been practiced on static pages, not as the foundation of a single-page application.
